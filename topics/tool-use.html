Tool Use (Function Calling)

Tool use (also called function calling) is the mechanism that allows an LLM to take actions beyond generating text — by outputting structured requests that a system executes on its behalf, returning real-world results back to the model.

What is Tool Use?

By default, an LLM is text-in, text-out. It can reason brilliantly, but it cannot check today's weather, query a database, or send an email. Tool use bridges this gap: the model outputs a structured function call (name + arguments), the host system executes it, and feeds the result back. The model never runs code itself — it requests actions and interprets results.

This is the foundational mechanism that makes AI agents possible. Without tools, an LLM can only advise. With tools, it can act.

The Tool-Use Loop

The standard architecture powering all AI agents is a loop:

  1. Observe: The model receives context (user request, previous results)
  2. Think: The model reasons about what to do next
  3. Call Tool: The model outputs a structured function call
  4. Get Result: The system executes the call and returns the result
  5. Decide: The model evaluates the result — either calls another tool or responds to the user

This loop repeats until the model decides the task is complete. A single user request might trigger 1 tool call or 50, depending on complexity.

How It Works (Technical)

  1. Tool definitions are provided in the system prompt — each tool has a name, description, and parameter schema (usually JSON)
  2. The model decides to call a tool instead of generating a text response
  3. The system executes the function (API call, database query, file operation)
  4. The result is returned to the model as a new message
  5. The model continues reasoning with the new information

Best Practices (2026)

  • Start with one tool: Build an agent that calls a single function reliably before adding more
  • Write excellent descriptions: Tool descriptions are the highest-leverage optimization. Instead of "Search the web," use "Search the web for current information. Use when the user asks about recent events or data that may have changed since training."
  • Dynamic loading at scale: 50+ tool definitions consume ~55,000 tokens in the system prompt. The solution is loading a relevant subset per task via semantic search over tool descriptions
  • Set iteration limits: Always set max_iterations (5–10) to prevent infinite loops
  • Typed error signals: Return structured errors, not empty results. "Rate limited, retry in 3s" is far more useful than an empty array
  • Log everything: Every function call with user context, arguments, result, and timestamp — essential for debugging and compliance

Layman's Analogy

An LLM without tools is like a brilliant advisor locked in a room with no phone or computer. They can give amazing analysis — but cannot check today's stock price, send an email, or look up a customer record. Tool use gives them a phone, a computer, and a filing cabinet. They still don't physically do the work — they write a request on a slip of paper, slide it under the door, and someone on the other side executes it and slides the answer back.

Real-World Example: Claude Code

Claude Code uses tool calls for everything: Read File (to understand code), Edit File (to make changes), Run Bash (to execute tests), Search (to find relevant files). Each action is a structured tool call — Claude never directly touches the filesystem. It requests, the system executes, and the result comes back for Claude to reason about next.
