Skill markdown vs. MCP tool definition

Flipping a connector does not load a skill. It loads tool definitions, which sit in a different section of the model's input than skill markdown does, and which Claude interacts with using a different mechanism. Here is what each one literally looks like.

// IF you loaded a skill

What context looks like

A skill is markdown. It gets read like any system message. Claude responds in plain text, using the skill's instructions as guidance.

claude's context (excerpt)
[system message] You are Claude... [loaded skill: gmail-helper/SKILL.md] --- name: gmail-helper description: Helps draft emails matching the user's writing style. --- # Gmail Helper When the user asks for help with email: 1. Ask for the recipient and subject if not given 2. Match their usual tone (check past examples) 3. Keep it under 200 words unless asked otherwise 4. Suggest a subject line that is specific [user] draft a follow up to my boss about the Q2 review [assistant] Here is a draft. You will need to send it yourself. Subject: Following up on Q2 review next steps Hi, Wanted to circle back on...
The catch: the skill knows nothing about your actual emails. It cannot read your boss's name from previous threads, cannot see your writing style, cannot send the draft. Pure procedure applied blindly to whatever you typed.
// IF you toggled gmail mcp on

What context looks like

An MCP connector adds tool definitions to a separate section. Claude doesn't read these as text. It can invoke them, get real data back, then respond.

claude's context (excerpt)
[tools] [ { "name": "gmail_search", "description": "Search messages in Gmail.", "input_schema": { "type": "object", "properties": { "query": { "type": "string" }, "max_results": { "type": "integer" } }, "required": ["query"] } }, { "name": "gmail_send", "description": "Send an email from the user's account.", "input_schema": { /* to, subject, body */ } }, { "name": "gmail_get_thread", /* ... */ } ] [user] draft a follow up to my boss about the Q2 review
The shape: no instructions, no procedure, no markdown. Just a structured registry of callable functions. Claude sees their names, descriptions, and argument shapes. It can call any of them by emitting a structured tool_use block.
// the tool call cycle

What happens after Claude sees the tool list

Hit play to step through what happens when you ask "draft a follow-up to my boss about the Q2 review" with the Gmail MCP tools available. This is the loop that makes tools different from skills.

USER
turn 01
"Draft a follow-up to my boss about the Q2 review."
CLAUDE
turn 01 reply
Thinks: "I should look at the actual Q2 review thread before drafting." Emits a structured block, not text:

tool_use { name: "gmail_search", input: { query: "from:boss subject:Q2 review", max_results: 5 } }
HOST
intercepts
Claude Desktop catches the tool_use block before you see anything. Translates it into an MCP call and sends it to the Gmail MCP server running in the background.
MCP SERVER
executes
The Gmail MCP server takes the query, makes the real Gmail API call using your OAuth token, gets back five threads, returns them via MCP.
HOST
injects result
Wraps the response in a tool_result block and feeds it back into Claude's context:

tool_result { content: [{ subject: "Q2 review notes", from: "anna@...", snippet: "Great review yesterday, here are the action items..." }, ...] }
CLAUDE
turn 01 final
Now armed with the actual thread, Claude writes the real draft, referencing specific action items from Anna's email. This is the text you finally see in the chat.

A skill is text Claude reads and follows. A tool is a button Claude can press. Both live in Claude's input but they sit in different sections and Claude interacts with them differently.

Flipping a connector ON adds tool definitions. It does NOT load a markdown instruction file. The "knowledge" of how Gmail's API works never enters Claude's context. That knowledge lives inside the MCP server, hidden behind the tool's name and schema. Claude only ever sees the door, never the lock.

Is the tool description maintained by Gmail?
Half right. What's maintained is the MCP server program, not a text file. When your Claude session starts, the host asks each connected server tools/list and the server replies with its current tool definitions. Those get injected fresh every session. If Google changes Gmail's API tomorrow, whoever maintains the Gmail MCP server (Anthropic for the official one) updates the server. You pull the update. Next session, Claude automatically discovers any new tool shape.
So flipping the switch DOES change Claude's context, then?
Yes, but not in the place you were imagining. Every Claude API call has three fields: system, tools, and messages. A skill goes into the system field. An MCP connector goes into tools, as structured function declarations. Both consume tokens. Both affect what Claude can do. But they are processed differently.
If the tools section also costs tokens, how is this any different from skill text?
Three big differences. One: Claude cannot fabricate a tool call. If gmail_send is not declared, Claude cannot pretend to send mail. With a skill that explains the API, Claude could hallucinate a fake response. Two: tools return real data. The result of gmail_search is whatever Gmail actually returned, byte for byte. Three: the messy code (OAuth, retries, parsing) stays out of Claude's context.
Does Claude ever "see" my Gmail OAuth token or API key?
No. The token is held by the MCP server and the host that launched it. Claude only sees the tool's input schema and the cleaned-up result. This is why MCP is more secure than baking secrets into a skill: credentials never enter the model's context, so they cannot leak through a prompt injection.
Can a Skill and an MCP tool work together?
Yes, and this is how mature setups work. The skill provides the procedure ("when drafting a follow-up email, first fetch the original thread, identify open action items, then draft a response that addresses each one"). The MCP tool provides the capability (the actual ability to fetch threads and send mail). Skills tell Claude what to do. MCP tools let Claude do it. Complementary, not competing.
