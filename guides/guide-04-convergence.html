// chapter 04 // the deep stuff

The skill that calls an API, the field that holds tools, and the hybrid that already exists

Three sharp questions, three precise answers. A real skill from the skills.sh directory is the case study. The API structure is the diagram. Tool Search is the answer to "why can't tools load conditionally too." Plugins are the hybrid people keep asking about.

// question 01

"If a skill calls an API, isn't it just a tool?"

It looks that way, but a skill never directly touches the network. It commands a tool that Claude already had to do the touching. Here is the actual chain for the inference.sh image-generation skill from skills.sh.

📄
SKILL
markdown text loaded into context
🧠
CLAUDE
reads the skill, decides to act
⚙️
BASH TOOL
Claude's built-in. emits tool_use for shell command
🖥️
belt CLI
runs on your machine, parses args
☁️
inference.sh
the actual HTTP API call
🖼️
IMAGE URL
flows back through every step
six links in the chain. only step three is a "tool" in the Claude sense.
The real lesson: a skill is inert markdown. It needs an existing tool (Bash here, but could be Python execution, web fetch, anything) to actually do work in the world. The skill orchestrates. The tool executes. The CLI bridges the tool to the API. The skill never "becomes" a tool; it directs one. Without Claude having a Bash tool, this skill does literally nothing.
# what claude actually emits when running this skill tool_use { name: "Bash", input: { command: "belt app run falai/flux-dev-lora --input '{\"prompt\": \"a cat astronaut\"}'" } } # bash runs it. belt CLI hits inference.sh. URL comes back. # claude only ever called one tool: Bash.
// question 02

"Are tools in the same context as system instructions?"

There is one input the model reads. But that input is built from three distinct API fields in the request. Here they are.

system top-level field
The system prompt. Skills load here, or in a system-style block prepended to messages. persistent
tools top-level field
Array of structured tool declarations. Built-in tools (Bash, web_search) and MCP tools both live here. persistent
messages top-level field
The growing conversation: your turns, Claude's replies, tool_use and tool_result blocks. prunable
Your intuition was correct: when context fills up, the host's compaction logic typically prunes or summarizes old messages first. The system and tools fields are held constant across turns and survive compaction. So both skills and MCP tools are privileged residents of context, while old chat turns are tenants who can be evicted.
One caveat: "persistent" means "the host keeps sending them in every turn." If the compactor is dumb and the conversation runs really long, in theory they could rotate out. But every well-built client keeps system and tools at the top, every turn. Treat them as effectively permanent.
// question 03 // your real insight

"Why can't tools be conditionally loaded like skills?"

They can. Anthropic already shipped this. It's called Tool Search. Your hybrid intuition is exactly the direction the architecture is moving.

// OLD WORLD // all tools eager

Connect 15 MCP servers

Every tool from every server gets dumped into the tools field at session start. Hundreds of declarations, often 50,000+ tokens before you've typed anything.

49% accuracy on Opus 4 with crowded tool catalog
// NEW WORLD // tool search

Same 15 servers, lazy

Only a meta-tool tool_search is loaded by default. Real tool catalog sits indexed on the side. When Claude needs a capability, it searches by keyword and only the matching tools enter context.

74% accuracy on the same workload, same Opus 4
# turn 1: claude sees only the meta-tool tools: [ { name: "tool_search", description: "find tools by keyword" } ] # user: "send a message to the engineering slack channel" # claude calls the meta-tool first tool_use { name: "tool_search", input: { query: "slack message post channel" } } # host returns matching tools, injects them for this turn only tool_result: "found 3 tools: slack_send_message, slack_list_channels, slack_get_user" # now claude calls the real tool tool_use { name: "slack_send_message", input: { channel: "engineering", text: "..." } } # the other 14 servers' tools never entered context this turn.
Identical in spirit to skill progressive disclosure. Skills scan descriptions, load bodies on match. Tool Search scans tool names and descriptions, loads schemas on match. Two implementations of the same idea: do not pay token cost for things you have not used yet.
// question 04 // the hybrid already exists

"Couldn't skills just include MCP tools?"

That's a plugin. A plugin is the bundle that ships skills and MCP servers together, each obeying its own loading rules.

// skills/ (progressive disclosure)
  • flux-prompt-engineer/ SKILL.md teaches Claude how to craft FLUX prompts
  • character-consistency/ SKILL.md explains seed reuse for character lock
  • style-transfer/ SKILL.md walks through reference image workflows
// .mcp.json (tool search lazy load)
  • generate_image tool to call inference.sh
  • generate_video tool for Veo, Seedance, etc.
  • upscale_image tool for super-resolution
  • get_job_status tool for async jobs
The two halves work together. When a user asks "make a consistent character across three poses," the character-consistency skill fires (progressive disclosure, body loads). The skill's procedure tells Claude to call the generate_image tool three times with a fixed seed. That tool gets located via tool search and called. Skill = procedure. Tool = capability. Plugin = the box they ship in.

Skills, tools, and plugins are not three different things so much as three layers of the same idea. Skills are procedural knowledge. Tools are callable capabilities. Plugins are bundled distribution. The loading discipline is converging: only pay for what you use, only in the moment you need it.

The image skill from skills.sh, the Gmail MCP connector, the legal-counsel plugin from last week are all doing variations of the same dance: keep the catalog small and indexed, expand the specific piece on demand, throw it away when done. The vocabulary differs. The shape is the same.
